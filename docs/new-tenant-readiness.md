# Готовность к посадке новых фирм: что проверено и где тонко

Анализ от 13.08.2026 перед началом продаж — что происходит, когда в системе
появляется вторая, третья, десятая бухфирма.

Изоляция (этапы 1–4 SaaS) сделана и на проде. Ниже — не пересказ архитектуры, а
результат проверки: что держит, что сломается тихо, и что проверить на проде.

---

## Что проверено и держит

| Проверка | Результат |
|---|---|
| `TenantGuardTest` — новая таблица/модель без `tenant_id` роняет тест | зелёный, сторож работает |
| `TenantIsolationTest`, `TenantSchemaTest`, `TenantRegistrationTest`, `TenantTemplateTest`, `VendorPanelTest` | 62 теста зелёные |
| Сырой SQL мимо Eloquent | 4 запроса в `AppServiceProvider`, у всех дописан `where('tenant_id', ...)` вручную |
| Модели рабочих таблиц | трейт `BelongsToTenant` на месте; `client_import_rows` намеренно без него (привязка через родителя, объявлено в стороже) |
| Ночной воркер `tasks:generate` | ходит по `Tenant::real()` внутри `TenantContext::for()`, аккаунт-образец исключён |
| История задач на карточке клиента (новое) | добавлены тесты: список, карточка задачи и документ чужой фирмы дают 404 |
| Octane | не используется, значит статические кэши живут в пределах одного запроса |

**Хардкод категорий БП безопасен.** `Service::MANDATORY_CATEGORIES = ['Обязательная']`
сверяется по точному названию, но таблица `categories` — **общая** для всех фирм
(в списке `SHARED_TABLES` вместе с `periodicities`, `tax_systems`, `roles`, `modules`).
Новая фирма не может переименовать категорию у себя и сломать подтягивание в смету.

## Риски, по убыванию неприятности

### 1. Платные БП у новой фирмы стоят 0 сом — молча

`TenantTemplate::copyServices()` при копировании из образца **обнуляет `rate_id`** —
и это правильно, ставки это цены, чужие показывать нельзя. Но `PricingCalculator`
для режимов `by_quantity` / `addon` без ставки возвращает `0.0`:

```php
if (in_array($code, Billing::PAID_CODES, true)) {
    return $service->rate ? (float) $service->rate->price : 0.0;
}
```

В локальной проверке у свежей фирмы «Ромашка» — 2 платных БП, **оба без ставки**.
В смете они встанут по 0 сом без единого предупреждения, и фирма выставит счёт с
дырой.

**Что сделать:** предупреждение в смете и в каталоге БП — «тарифицируется по ставке,
ставка не задана». Чинится в UI, миграции не нужны.

### 2. Пустой аккаунт-образец = тихо пустая фирма

`TenantTemplate::template()` падает, только если образца **нет вообще**. Если он
есть, но пустой (или его почистили через `clearTemplate()`), `copyTo()` скопирует
ноль строк, регистрация пройдёт успешно, а фирма получит пустой каталог БП и не
сможет собрать ни одной сметы. `TenantRegistrar::register()` результат копирования
не проверяет.

**Что сделать:** после `copyTo()` убедиться, что БП скопировались, иначе не
регистрировать (или регистрировать с явным предупреждением).

### 3. Связь БП с режимом биллинга — по названию, плюс кэш без учёта фирмы

`services.billing` хранит **название** режима («Считается по количеству»), а код
резолвится через `Billing::codeForName()` — поиском по названию в тенантной таблице
`billings`. Две тонкости:

- Фирма переименует режим в настройках → `codeForName()` вернёт `null` → цена молча
  уедет на `services.cost` вместо ставки.
- `Billing::$codeByNameCache` — статический кэш «название → код» **без ключа фирмы**.
  Сейчас безвреден (Octane нет, воркер цены не считает), но станет ошибкой, если
  появится Octane или консольная команда, считающая цены по нескольким фирмам подряд.

**Что сделать:** хранить в `services.billing` код, а не название (миграция с
перекладкой), либо как минимум добавить `tenant_id` в ключ кэша.

### 4. Статус фирмы нигде не проверяется

`AuthController::login()` смотрит только на статус сотрудника. `tenants.status`
(`trial` / `active` / `suspended`) не проверяется ни при входе, ни в middleware.
Приостановленная фирма работает как обычная — рычага «не заплатили» нет.

Это известное отложенное решение, не регресс. Но перед продажами стоит вернуть:
рекомендую жёстко (не пускать) + задачи генерить всегда, иначе после оплаты в
задачах будет дыра.

### 5. Почта сотрудника уникальна на всю систему

Это логин, решение осознанное. Следствие: один человек не может работать
бухгалтером в двух фирмах на этой платформе — при заведении получит «зарегистрируйтесь
с другого адреса». Для рынка, где бухгалтеры подрабатывают в нескольких конторах,
это всплывёт. Лечится только memberships (отложено).

### 6. Не баг, но будет вопросом №1 при онбординге

Новая фирма заводит клиента и смету — и не видит задач:

- месяц создания сметы холостой, задачи идут с 1-го числа следующего месяца;
- горизонт планирования 30 дней;
- `GenerateTaskReminders::BACKLOG_CUTOFF = '2026-07-01'` — старее этой даты
  напоминания не генерируются вообще.

Посадили клиента 15 августа → первые задачи 1 сентября. Стоит написать это в
памятке по онбордингу, иначе будет выглядеть как поломка. Подробнее — `docs/estimate-logic.md`.

## Проверить на проде перед посадкой первой новой фирмы

**1. Образец наполнен?**

```sql
SELECT t.id, t.name, t.status, t.is_template,
       (SELECT count(*) FROM services WHERE tenant_id = t.id) AS bp,
       (SELECT count(*) FROM billings WHERE tenant_id = t.id) AS billings,
       (SELECT count(*) FROM rates    WHERE tenant_id = t.id) AS rates
FROM tenants t
ORDER BY t.id;
```

У строки с `is_template = true` должно быть ненулевое `bp` и ровно 4 `billings`.
Если `bp = 0` — сначала наполнить: `php artisan tenant:fill-template`.

**2. Платные БП без ставки — у образца и у каждой фирмы**

```sql
SELECT s.tenant_id, count(*) AS paid_without_rate
FROM services s
JOIN billings b ON b.name = s.billing AND b.tenant_id = s.tenant_id
WHERE b.code IN ('by_quantity', 'addon')
  AND s.rate_id IS NULL
GROUP BY s.tenant_id;
```

Всё, что здесь вылезет, в смете посчитается как 0 сом.

**3. Сироты: БП, чей режим не находится по названию**

```sql
SELECT s.tenant_id, s.id, s.name, s.billing
FROM services s
LEFT JOIN billings b ON b.name = s.billing AND b.tenant_id = s.tenant_id
WHERE s.billing IS NOT NULL AND b.id IS NULL;
```

Пусто — хорошо. Непусто — у этих БП цена считается по `services.cost`, а не по ставке.

**4. Строки без хозяина** (должно быть пусто везде)

Это же проверяет `TenantGuardTest`, но на проде данные другие:

```sql
SELECT 'clients' AS t, count(*) FROM clients WHERE tenant_id IS NULL
UNION ALL SELECT 'services',      count(*) FROM services      WHERE tenant_id IS NULL
UNION ALL SELECT 'estimates',     count(*) FROM estimates     WHERE tenant_id IS NULL
UNION ALL SELECT 'estimate_items',count(*) FROM estimate_items WHERE tenant_id IS NULL
UNION ALL SELECT 'buh_task_logs', count(*) FROM buh_task_logs WHERE tenant_id IS NULL
UNION ALL SELECT 'employees',     count(*) FROM employees     WHERE tenant_id IS NULL;
```

## Порядок работ, если чинить

1. Предупреждение о платном БП без ставки (риск 1) — самое дешёвое и самое денежное.
2. Проверка непустого копирования при регистрации (риск 2).
3. Статус `suspended` блокирует вход (риск 4) — нужен до первых платящих.
4. Биллинг по коду вместо названия (риск 3) — миграция, делать не в спешке.
