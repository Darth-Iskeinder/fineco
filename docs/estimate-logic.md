# Логика сметы: какие БП подтягиваются клиенту и как

Документ описывает, как формируется смета клиента — какие бизнес-процессы (БП) из
каталога попадают на экран сметы, какие из них включены сразу, что происходит при
сохранении и почему БП может «не дойти» до бухгалтера.

**Код:** `app/Http/Controllers/EstimateController.php` (методы `edit()` и `save()`),
правила категорий — `app/Models/Service.php`, цена — `app/Services/PricingCalculator.php`.

---

## 1. Два разных понятия: «подтянулся» и «включён»

Это главное различие, из-за которого чаще всего возникает путаница.

| Понятие | Что значит | Где живёт |
|---|---|---|
| **Подтянулся** | БП виден в списке на экране сметы (строкой с тумблером) | только на экране, в базе ничего нет |
| **Включён** | тумблер БП стоит в положении «вкл» | на экране |
| **В смете** | после сохранения появилась строка в `estimate_items` | база |

Задачи бухгалтеру рождаются **только из сохранённых строк `estimate_items`**
(см. `BuhTasksController`). Подтянутый, но выключенный БП задач не создаёт и в
PDF-смету не попадает.

---

## 2. Один клиент — одна смета

Смета создаётся автоматически при первом открытии экрана:

```php
Estimate::firstOrCreate(['client_id' => $client->id], ['total' => 0]);
```

У клиента всегда ровно одна смета. Она может существовать пустой (без единой позиции) —
это нормальное состояние до первого сохранения.

**Первая загрузка** (`$isFirstLoad`) — это когда у сметы **нет ни одной сохранённой
корневой позиции**. Не «первое открытие страницы», а именно «смету ещё ни разу не
сохраняли». Только на первой загрузке действуют дефолты тумблеров. На всех
последующих загрузках побеждает сохранённое состояние.

---

## 3. Что подтягивается: три прохода

Список БП на экране собирается тремя последовательными проходами. БП, добавленный
в предыдущем проходе, во второй раз не добавляется (защита от дублей через
`$includedServiceIds`).

Общие условия для **любого** прохода (иначе БП не попадёт вообще никуда):

- `parent_id IS NULL` — корневой БП, а не подпункт (`scopeRoots`)
- `is_active = true` (`scopeActive`)
- совпадает `tenant_id` — БП принадлежит той же фирме (глобальный скоуп `BelongsToTenant`)

Порядок внутри списка: `sort_order`, затем `name` (`scopeOrdered`).

### Проход 1 — по режиму налогообложения (РН) + обязательные

```php
$rootServices = Service::roots()->active()->ordered()->get()
    ->filter(function ($s) use ($matchesTaxSystem, $clientIsZero) {
        if ($clientIsZero && Service::isMandatoryCategory($s->category)) {
            return false;
        }
        return $matchesTaxSystem($s) || Service::isMandatoryCategory($s->category);
    });
```

БП подтягивается, если выполнено **хотя бы одно**:

- **Совпал РН**: `clients.tax_system_id` есть в списке РН этого БП
  (таблица связи `service_tax_system`). Категория при этом роли не играет —
  так тянется, например, «Условная по профилю».
- **Категория «Обязательная»**: тянется всем, даже если РН не совпал.

**Исключение — клиент-нулёвка** (`clients.is_zero_movement = true`): обязательные БП
ему не тянутся **вообще**, даже если РН совпал. Проверка на нулёвку стоит раньше
проверки РН, поэтому она «сильнее».

### Проход 2 — по особым условиям клиента

Для каждого условия из `Service::SPECIAL_FLAGS` (сотрудники, ККМ, алкоголь, импорт ЕАЭС,
экспорт, ОС, ГСМ, кредиты, акциз и т.д.):

- если у клиента включён триггер-признак (`clients.has_employees`, `clients.has_kkm`, …),
- подтягиваются все активные корневые БП с соответствующей колонкой (`services.is_employees`,
  `services.is_kkm`, …), которых ещё нет в списке.

**Без фильтра по РН и без учёта категории.** Достаточно совпадения флага.

### Проход 3 — рекомендованные контрольные

БП категории `'Рекомендованная контрольная'` подтягиваются **всегда**, независимо
от РН и особых условий, если ещё не добавлены.

Отличие от остальных: на первой загрузке их тумблер **выключен** — бухгалтер сам
решает, брать их клиенту или нет.

> Асимметрия, о которой стоит знать: клиенту-нулёвке рекомендованные контрольные
> тянутся (проверки на `is_zero_movement` в этом проходе нет), а обязательные — нет.

## 4. Категории БП

Хардкод по названию категории в `app/Models/Service.php`:

```php
public const RECOMMENDED_CATEGORIES = ['Рекомендованная контрольная'];
public const MANDATORY_CATEGORIES   = ['Обязательная'];
```

Сравнение — **строгое совпадение строки** после `trim()`. «Обязательные»,
«обязательная» с маленькой буквы, лишний символ внутри — уже не сработают,
БП молча потеряет особый режим и будет тянуться только по совпадению РН.

| Категория | Как подтягивается | Тумблер на первой загрузке |
|---|---|---|
| `Обязательная` | всем, кроме нулёвки; РН не нужен | включён |
| `Рекомендованная контрольная` | всем всегда; РН и флаги не нужны | **выключен** |
| Любая другая (напр. «Условная по профилю») | только по совпадению РН или по особому условию | включён |

> TODO в коде: вынести поведение в справочник категорий (поле вида
> `default_mode: auto | recommended`), чтобы каждая бухкомпания настраивала режим
> подтягивания на самой категории, а не по названию.

## 5. Состояние тумблера

```php
'enabled' => $isFirstLoad
    ? !Service::isRecommendedCategory($bp->category)
    : ($savedItem !== null),
```

- **Первая загрузка** (смета ни разу не сохранялась): всё включено, кроме
  рекомендованных контрольных. Подпункты (children) — всегда выключены.
- **Все последующие загрузки**: тумблер = «есть ли сохранённая строка в `estimate_items`».
  Категория больше не влияет.

### Следствие: новый БП в старой смете

Если БП завели в каталоге **после** того, как смету клиента уже сохранили, — он
подтянется на экран, но с **выключенным** тумблером, потому что сохранённой строки
для него нет. В смету он попадёт только когда бухгалтер вручную включит тумблер и
сохранит.

Правило категории «Обязательная» **не переоткрывает** уже сохранённые сметы.
Это ровно тот случай, из-за которого «Счёт за услуги ФинЭко» и «АВР» могут
отсутствовать у части клиентов на проде.

## 6. Филиалы: размножение строк

Если у БП стоит `splits_by_branch = true` **и** у клиента есть филиалы
(`has_branches = true` и хотя бы у одного филиала заполнен `no_code`), БП
превращается в несколько строк — по одной на каждый налоговый орган:

- основной НО клиента (`clients.tax_office_code`) с подписью «основной»,
- плюс по строке на каждый филиал с заполненным `no_code`.

Название филиала берётся из справочника `tax_authorities` по коду, а не из снимка
в `branches.city` — иначе устаревший город разойдётся с кодом.

Ключ строки: `service_id + tax_office_code`. На один БП приходится несколько строк
с одинаковым `service_id`, различающихся кодом НО.

Стоимость при этом **не умножается** на число филиалов — цена берётся как у обычного
БП (умножение ×N осознанно отложено).

---

## 7. Цена строки

`PricingCalculator` — единственный источник цены. Режим биллинга БП решает всё:

| Режим (`billing`) | Цена за единицу |
|---|---|
| `included` / `none` (FREE_CODES) | 0 — входит в абонентку / не тарифицируется |
| `by_quantity` / `addon` (PAID_CODES) | цена привязанной ставки (`services.rate_id` → `rates.price`) |
| режим не задан | откат на собственный `services.cost` (обратная совместимость) |

Сумма строки = цена за единицу × количество (количество ≥ 0, округление до копеек).
Единица измерения (`rates.unit`) — только подпись, на расчёт не влияет.

Если у БП есть включённые подпункты, сумма родителя = сумма подпунктов, а не
собственная цена БП.

## 8. Тарифные БП против доп. услуг

На экране два блока, и разделение проходит по одному признаку:

**Тарифная позиция** — строка, чей БП реально подтянулся этому клиенту в этот раз
(ключ `service_id + tax_office_code` есть среди подтянутых) **и** `type = 'recurring'`
**и** это первая такая строка.

**Доп. услуга** — всё остальное: строки без `service_id` (своя услуга, вписанная
руками), строки БП, который клиенту не подтянулся, и вторая строка того же БП
(тот же БП добавили и в тариф, и вручную).

> Историческая заметка: раньше тарифной считалась любая строка `recurring + service_id`.
> Из-за этого доп. услуга из каталога с типом «Постоянная» после сохранения либо
> всплывала в блоке тарифа, либо пропадала с экрана — оставаясь в базе и продолжая
> порождать задачи, — а следующее сохранение удаляло её вместе с логами задач.

## 9. Сохранение: reconcile, а не «снести и создать заново»

`save()` **обновляет позиции на месте**, а не удаляет и создаёт заново. Это критично:
`buh_task_logs` привязаны к `estimate_items.id`, и пересоздание строки стирало бы
историю задач каскадом (в т.ч. задачи «на проверке»).

Алгоритм:

1. Для каждой существующей корневой позиции считается стабильный ключ:
   - есть `service_id` → `svc:{service_id}:{tax_office_code}:{branch_label}`
   - нет `service_id` (своя услуга) → `name:{имя в нижнем регистре}:{type}`
2. Строки складываются в очередь по ключу (несколько строк на ключ — нормально).
3. Приходящие строки разбираются по порядку — **тарифные первыми**, затем доп. услуги.
   Совпавшая по ключу строка забирается из очереди («использована»), обновляется на
   месте, её `id` сохраняется.
4. Не совпавшие — создаются заново.
5. Строки, оставшиеся в очереди, удаляются вместе с подпунктами. Их `buh_task_logs`
   уходят каскадом — это осознанно: БП убрали из сметы.

**Выключенный тумблер = строка не пришла = позиция удаляется** вместе с историей
задач по ней. Снятие тумблера — не «пауза», а удаление.

Исполнитель строки (`assignee_id`) может задать только главбух этого клиента или
админ (`canAssign()`). У остальных поле read-only, при сохранении остаётся прежний
исполнитель, а если его не было — ответственный за клиента.

### Смена ответственного у клиента

Ответственный (`clients.responsible_employee_id`) и исполнитель строки (`assignee_id`)
это разные поля, поэтому смена ответственного сама по себе смету не двигала: клиент
числился за новым сотрудником, а задачи продолжали генерироваться на прежнего. У
уволенного работа зависала совсем.

Теперь при сохранении карточки клиента с новым ответственным работает
`ClientResponsibleTransfer` (одной транзакцией вместе с самим сохранением):

| Что | Переносится на нового |
|---|---|
| Корневые позиции сметы, где исполнителем стоял прежний ответственный | да |
| Позиции без исполнителя (`NULL`) | да, исполнитель проставляется явно |
| Позиции, отданные другим бухгалтерам | нет, сменился главбух, а не они |
| Подпункты позиций | нет, исполнителя у них нет |
| Незакрытые напоминания (`task_reminders`, `pending`) | да |
| Выполненные напоминания (`done`) | нет, история прежнего |
| Внеплановые задачи в работе (`pending`, `running`, `paused`, `rework`) | да, со сбросом `assign_seen_at` |
| Внеплановые задачи в `review` и `completed` | нет |
| Логи плановых задач (`buh_task_logs`) | нет, кто что делал не переписываем |

Напоминание, которое у нового исполнителя уже есть на тот же БП и срок, не переносится,
а удаляется: ключ `(employee, client, service, due_date)` уникален.

Дальше `tasks:generate` идёт по `assignee_id`, поэтому все новые задачи создаются уже
на нового сотрудника. Задачи на проверке тоже переходят к нему сами: проверяющий нигде
не хранится, он вычисляется по текущему ответственному.

Если ответственного **сняли** (стало пусто), не переносится ничего: работа остаётся на
прежнем сотруднике, а клиент пропадает из БухСметы и задачника у всех, кроме админа и
руководителя.

Правило работает в трёх местах, где меняется поле: быстрая правка в списке клиентов,
секция «Договор» в карточке и импорт клиентов из CSV.

## 10. Срок выполнения строки

Периодичность и день срока берутся **из БП**, а не из присланных с экрана данных —
и для тарифных строк, и для доп. услуг из каталога.

У клиента может быть индивидуальное расписание, переопределяющее дефолт БП
(`client_service_schedules`, keyed by `service_id`). Эффективное расписание считает
`Service::resolveForClient($override)`.

У своей услуги (без `service_id`) расписания нет — блок срока для неё не показывается.

## 11. Что происходит после сметы

Смета — источник задач, но не сами задачи. Из сохранённых `estimate_items` строятся
задачи бухгалтеру. Здесь работают отдельные правила, которые стоит держать в голове
при разборе «задача не пришла»:

- месяц создания сметы **холостой** — задачи идут с 1-го числа следующего месяца;
- горизонт планирования — 30 дней, более дальние задачи попадают в блок
  «Запланировано позже»;
- БП без `start_day` и все БП с периодичностью «Разовая» задач не порождают (молча).

Выполненные задачи по клиенту видно в секции «История задач» внизу карточки клиента
(`app/Services/ClientTaskHistory.php`).

## 12. Диагностика: «БП не попал в смету»

Проверять по шагам, сверху вниз.

**Шаг 1. Паспорт БП** — все базовые условия сразу:

```sql
SELECT id, tenant_id, name, parent_id, is_active,
       '[' || category || ']' AS category_raw,
       length(category)       AS cat_len,
       periodicity, start_day, sort_order
FROM services
WHERE name ILIKE '%ФинЭко%' OR name ILIKE '%АВР%';
```

Ожидаем: `parent_id` = NULL, `is_active` = t, `category_raw` = `[Обязательная]`
(длина 12), `tenant_id` — нужная фирма.

**Шаг 2. Как записаны категории** — ловим опечатки и дубли:

```sql
SELECT '[' || COALESCE(category, 'NULL') || ']' AS category_raw,
       length(category) AS len, count(*) AS bp_count
FROM services
WHERE parent_id IS NULL
GROUP BY 1, 2
ORDER BY bp_count DESC;
```

**Шаг 3. Охват** — в скольких сметах БП реально есть:

```sql
SELECT s.id, s.name,
       count(DISTINCT ei.estimate_id) AS in_estimates,
       (SELECT count(*) FROM estimates) AS total_estimates
FROM services s
LEFT JOIN estimate_items ei ON ei.service_id = s.id
WHERE s.name ILIKE '%ФинЭко%' OR s.name ILIKE '%АВР%'
GROUP BY s.id, s.name;
```

**Шаг 4. Кому не попало и почему**:

```sql
SELECT c.id, c.name, c.is_zero_movement, e.id AS estimate_id,
       e.created_at AS estimate_created,
       s.name AS missing_bp
FROM estimates e
JOIN clients c ON c.id = e.client_id
CROSS JOIN services s
WHERE (s.name ILIKE '%ФинЭко%' OR s.name ILIKE '%АВР%')
  AND s.parent_id IS NULL
  AND NOT EXISTS (
      SELECT 1 FROM estimate_items ei
      WHERE ei.estimate_id = e.id AND ei.service_id = s.id
  )
ORDER BY c.name, s.name;
```

Трактовка результата:

| Что видим | Диагноз |
|---|---|
| `is_zero_movement = t` | работает по спеке — нулёвке обязательные не тянутся |
| `is_zero_movement = f`, смета создана раньше БП | тумблер пришёл выключенным (раздел 5) |
| категория написана иначе | опечатка в каталоге, БП тянется только по РН |
| `is_active = f` или `parent_id` не NULL | БП отключён или заведён подпунктом |
| `tenant_id` другой | БП принадлежит другой фирме |
